# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is an **RDF/OWL ontology project** — a formal semantic knowledge model for representing natural people's identity data in Tellipod, a free, open-source application under development at The Mee Foundation. It comprises two peer application ontologies (`persona.ttl`, `pod.ttl`) and the pod categories (`pod-categories.ttl`), plus `service.ttl` (the non-human, member-capable participants — AI agents, pod backup services, and the services organizations provide) and a growing family of `other/` peer ontologies for domains a person merely *has* rather than *is*:

- **Persona ontology** (`persona.ttl`): models identity data — names, addresses, identifiers, relationships, payment cards, and more — structured around graph-specific `Person` instances. Imports and profiles existing domain ontologies, documenting which of their classes and properties Tellipod uses, and extends them with app-specific terms.
- **Pod ontology** (`pod.ttl`): defines `pod:Pod` — the self-contained *content* facet of a pod, carrying only what's common to every pod: `category` (range `skos:Concept`, at most one value, absent/nil exactly when the pod is of the UserDefined category — identified precisely by the pod carrying no category value at all, not a vague judgment call (this repo's scaffolding mirrors it in the pod-databook filename's `(custom)` disambiguator) — otherwise the category concept the pod was originally instantiated as, a genuine `skos:Concept` individual scoped to `podcat:PodCategoryScheme` — pod-categories.ttl's tree is a SKOS concept scheme, not an OWL class hierarchy, so no class-value punning is involved here — fixed at creation and not re-derived from the pod's current name, so a pod can be freely renamed or moved without needing to update it), letting a recipient's app use it as a hint for where to file a shared pod in its own tree; referenced by name without `owl:imports pod-categories.ttl`. `pod:category` does not contradict `pod:Pod`'s "no link to a tree position" design, since its range is the classificatory `skos:Concept`, not a tree position — a pod's parent is per-member state in that member's own store, never shared content and never modelled here (see [storage.md](storage.md)). `pod:Pod` splits into two disjoint kinds (`owl:disjointWith` — a pod is always exactly one, never both): `pod:TemplatePod` (a reusable, class-level template, carrying `category` — the category concept it's a template for — `memberShape` (0..N, governing the eventual pod's `member` graphs) and `declaresTool` (0..N `pod:Tool` nodes naming the tools a pod of that category is created with, each carrying its own `formShape`; presence or absence is the whole of what a template says on the matter, there being no separate boolean to disagree with it)) and `pod:InstancePod` (concrete — every real pod instantiated in a user's own tree is typed directly `pod:InstancePod`, carrying `creator`, `owner`, `member`, and the two tag properties `userTag` (`xsd:string`) and `serviceTag` (an `owl:ObjectProperty` whose values are `pod:ServiceTag` nodes, each carrying `tagNamespace`/`tagKey`/`tagValue`, `xsd:string`, one apiece — the namespace being a DNS domain the writing module's own developer controls, written reverse-DNS), each 0..N — plain-string retrieval labels orthogonal to `category`'s single filing hint, a tag's kind being carried entirely by which of the two properties holds it; there is no app-supplied tag kind and no built-in tag vocabulary, since a set of pods sharing a fact the data already models is found by searching for that property instead; domain is `InstancePod` not `Pod`, so a `TemplatePod` seeds no tags and none is ever cloned by Lazy Instantiation, and `serviceTag` alone — written by one member's own service module, never displayed to the user and never findable by the user's own tag search, reachable only by the writing module through the app's Pod Interface and only within its own `tagNamespace` — is the one piece of a pod's content that never propagates on a share; member count is never itself stored, just counted from `member` when needed). A pod stores no shape of its own: an `InstancePod`'s applicable validation shape is never stored, only derived — reverse-lookup the `TemplatePod` with the same `category` value and read either its `memberShape` (for a `member` graph) or the `formShape` of the matching declared tool (for a tool's own graph), the same reasoning by which a pod stores no subject of its own (`pod:subject` exists, but is scoped to `pod:MemberGraph`, naming the party whose member entry a graph is rather than what the pod is about). There is no further pod subclass: "has a topic" could never distinguish one kind of pod from another, since every pod is about something — a two-member pod with no tool and an empty note is about the relationship between its two members. What varies is whether a pod holds *structured* content, and of what kind, which `tool` records as a count from zero upwards. `member` (an `owl:ObjectProperty`, range `pod:MemberGraph`, domain `InstancePod`) links to the required baseline of graph DataBooks backing the pod's content, one or more per member required, no fixed upper bound; `owner` (same domain, range `p:Person` — never a `service:Service` — matching `creator`'s own range) identifies which of the pod's members hold the owner role rather than the regular (non-owner) member role every other member defaults to — required, one or more values, no fixed upper bound; `creator`'s own value is always included among `owner`'s values as the pod's initial (and, until any promotion, sole) owner, and any current owner may promote any other current regular member (never a service) to owner, or demote another owner back to regular-member status (the `sh:minCount 1` floor keeps a pod's last remaining owner from being demoted); `tool` (range `pod:Tool`, domain `InstancePod`, 0..N, no upper bound) links to the objects the pod carries beyond that baseline — a form, a calendar, a drawing canvas or a map, each with its own data format and its own contribution to the app's UI; a pod with none is the ordinary case. Only the data format is modelled; the UI contribution is app-level. `pod:Tool` (abstract) carries no property of its own and splits into `pod:Form`, `pod:Calendar`, `pod:Canvas`, `pod:Contacts` and `pod:Map`; only `Form` has a content model, and all three tool-content properties are scoped to it — `formTopic` (what the content is about, `xsd:anyURI`, exactly one value on a live form tool), `formGraph` (range `pod:FormGraph`, at least one value, capped in practice at the pod's own member count, per tool — see integrity.md's YAML-8) and `formShape` (range `sh:NodeShape`, 0..N, declared-tool role only). Nothing sits on the abstract class: the four stub kinds have no data format of their own yet, so nothing has been shown common to all five, and hoisting later is cheaper than retracting. A tool node appears in two roles, told apart by which property points at it rather than by its class: reached by `tool` it is live, carrying `formTopic`/`formGraph` and never `formShape`; reached by `declaresTool` from a `TemplatePod` it is a declaration, carrying `formShape` alone. `formTopic` sits on the tool rather than on each graph beneath it because a tool's several graphs are one claim apiece by different members about one and the same thing — stating it once makes their disagreeing about it unrepresentable rather than merely forbidden. There is no pod-level subject property — who or what a pod's relationship is about is derived instead: the distinct `formTopic` values among its tools if any, else the distinct `subject` values among `member` (see integrity.md's YAML-4). Graph content comes from the graph-DataBook classes defined in this same file, since a graph DataBook only ever exists to be linked from a pod: `pod:Graph` (abstract) carries `shape` (the `sh:NodeShape` its content conforms to — i.e. the form the app renders for it; named for that and deliberately not "template", which names the wholly different class-level `pod:TemplatePod`); its abstract subclass `pod:CGraph` carries `claimant` (who claimed the data — a `p:Person`, `o:Organization`, or `service:Service`; a `service:ServiceProvider`'s content is attributed to the `service:providedBy` organization behind it rather than to the service itself); and `pod:CGraph` splits into two `owl:disjointWith` leaves, neither with subclasses of its own — `pod:MemberGraph` (`member`'s range) carrying `subject`, the party whose member entry the graph is, and `pod:FormGraph` (`formGraph`'s range) carrying no about-ness property of its own, its topic being the holding tool's single `formTopic`. The split is a PDN-layer one and is the whole point of having two leaves: a `claimant` or a `subject` value always maps to a PDN node "subject" identity, since both name parties, whereas a `formTopic` value need not and routinely does not — a pet, a vehicle, a passport, a recipe or a poem has no PDN subject identity and could never be given one, though a topic that happens to be a Tellipod user or an organization does have one. Nothing in a `tpod.member`/`tpod.tool[].graph` entry marks its own kind; the list it sits in settles it, matching `member`'s and `formGraph`'s ranges. The four self-vs-other combinations a member graph distinguishes (self-by-self, other-by-self, other-by-other, self-by-other) are derived directly from `subject`/`claimant`. A `pod:Pod` carries no tree position of its own. Every pod in a user's own tree is typed `pod:InstancePod`, never `pod:TemplatePod`, which is reserved for the reusable class-level templates in `pod-category-templates.ttl` — a purely organizational pod with nothing substantive to say still carries a minimal stub `member` entry (claimed by and about `:Self`, who is then also that pod's sole `owner` value) rather than omitting member content altogether, and (having nothing structured to hold) carries no `tool`. In app/user terminology, a **pod** is the atomic tree unit — held entirely inside the app, with pods nesting inside pods to form the tree; `pod:Pod` itself models only the content facet and stores no property for that tree position, which is per-member state in that member's own store (see [Key Architectural Patterns](#key-architectural-patterns)'s Pod/Category split note). In this repo a pod is carried on disk as a folder holding this pod-databook file, which is development scaffolding — see [storage.md](storage.md).
- **Pod categories** (`pod-categories.ttl`): defines the *classificatory* facet of a category — which kind of thing it is (e.g. `podcat:Work`, `podcat:Groups`; the `podcat:Person`/`podcat:Organization` top concepts and all narrower category concepts) — a `skos:ConceptScheme` (`podcat:PodCategoryScheme`), not an OWL class hierarchy: every category is a plain `skos:Concept` individual (there is no `podcat:Category` class at all), connected to its parent via `skos:broader` (asserted child → parent, one self-contained block per concept) and scoped to the scheme via `skos:inScheme podcat:PodCategoryScheme`. This is a deliberate fix for a real point of confusion: an earlier design used `rdfs:subClassOf` for this same tree, which wrongly implied OWL subsumption (`podcat:Pets rdfs:subClassOf podcat:Person` reads as "every Pet is a Person"). `skos:broader` carries no such entailment — `podcat:Pets skos:broader podcat:Person` means only that Pets is a narrower *topic* within the Person-rooted branch of information a user tracks about themselves, exactly the intended meaning. `pod-categories.ttl` defines no tree-position facet at all: a user's own instance-tree position is per-member state in that member's own store, with no RDF individual representing it at all, and `pod:category` (`pod.ttl`) is the sole remaining RDF-level record of a pod's matched classification. There is no `podcat:templatePod` property (removed) — a templated category's reusable starter content is instead found via `pod-category-templates.ttl`'s own `pod:TemplatePod` individuals, each of which carries its own `pod:category` value naming the category concept it's a template for (reusing `pod:category` rather than a separate forward-pointer property); finding the template for a given category is therefore a reverse lookup (`?tc pod:category podcat:X`), not a forward property chain, and `pod-categories.ttl` carries no `owl:imports` of `pod.ttl`/`pod-category-templates.ttl` at all any more, since nothing in it references a `pod:` term.

- **Other ontologies** (`other/`): small peer ontologies — one file per domain — for things a person merely *has* (a pet, a vehicle, an identity document, a medical appointment record, an online service account, a debit card and checking account, a residence, a trip itinerary, a record of one stage of their schooling) rather than *is*, keeping `persona.ttl` scoped strictly to a person's own identity. `persona.ttl` holds only the thin `hasX` link property for each domain that needs one at all (e.g. `persona:hasPet`, `persona:hasVehicle`, `persona:hasIdentityDocument`, `persona:hasBankAccount` — domain `p:Person`, range that domain's own class), referenced by name with no `owl:imports` in either direction — the same "referenced by name" pattern `pod.ttl` already uses for `pod:category`'s range (`skos:Concept`) and `pod:creator`'s range (`p:Person`/`o:Organization`). Several domains need no link property at all (service accounts reuse CCO's own `holds user account`; a residence, itinerary, or medical appointment record is simply the topic of its own pod's form tool), so `persona.ttl` adds nothing for them. Each `other/*.ttl` file's own template classes (e.g. `pets:Pet`, `vehicles:Vehicle`, `identitydocuments:IdentityDocument`, `medicalappointments:MedicalAppointmentRecord`, `serviceaccounts:ServiceAccount`, `banking:DebitCard`, `residences:Residence`, `itineraries:Itinerary`) are independent template type label classes, asserted via `rdf:type` directly on a graph's own content individual and targeted directly by their own SHACL shape — independent of `pod.ttl`'s `pod:shape` property, whose own range is `sh:NodeShape` (the SHACL shape that validates a graph's content, not the content's own class). Every one is paired with its own `other/shacl/<name>-shacl.ttl` shapes file: `other/pets.ttl`, `other/vehicles.ttl`, `other/identity-documents.ttl`, `other/medical-appointments.ttl`, `other/service-accounts.ttl`, `other/banking.ttl`, `other/residences.ttl`, `other/itineraries.ttl`, `other/education.ttl` — see [core-files.md](core-files.md).
- **Persona extension ontologies** (`persona-ext/`): the sibling family to `other/`, for terms whose subject is the `p:Person` themselves but which are too narrow to earn a place in `persona.ttl`. `other/education.ttl` and `persona-ext/directory-profile.ttl` are told apart by exactly one test — the **subject** of the properties in the file. An `other/` file's properties describe a record, document, or possession, an *independent* continuant with an existence of its own (`pets:hasSpecies` on a `pets:Pet`, `education:schoolName` on an `education:EducationRecord`); a `persona-ext/` file's properties have the `p:Person` as their subject, either with domain `p:Person` directly (`dp:hometown`, `dp:memberSince`) or with domain a *specifically dependent* continuant inhering in them — a BFO role or quality that could not exist without that person, reached from them by `BFO_0000196` (bearer of). `dp:jobFunction`, whose domain is CCO's Occupation Role (`cco:ont00000984`), is the one term currently taking the second route. `other/` never takes a `p:Person` property. Same one-file-per-domain shape and same `persona-ext/shacl/` subfolder convention. First member: `persona-ext/directory-profile.ttl`, the fields a membership directory asks of its members.
- **Category extensions** (`pod-category-ext/`): a bundle an organization publishes so that other instances of the app can file and validate pods of a category `pod-categories.ttl` does not define. One self-contained file per publisher carries its own `skos:ConceptScheme`, the `skos:Concept` individuals in it, and a `pod:TemplatePod` for each; its member shape sits beside it in `pod-category-ext/shacl/`. An extension concept links to the app's own taxonomy with **`skos:broadMatch`**, never `skos:broader` — SKOS reserves `skos:broader` for hierarchy within a single scheme and provides the `skos:mappingRelation` family for links between schemes — so that a recipient without the extension installed can still file an incoming pod under the core category it maps to. `pod-categories.ttl` and `pod-category-templates.ttl` never change to accommodate one. See integrity.md's TTL-8. First member: `pod-category-ext/boston-hub-society.ttl`, whose template pod is the first anywhere to name a `pod:memberShape` other than `pshapes:ContactInfoShape`.

There are no build, compile, test, or lint commands. The files are Turtle (`.ttl`) loaded into semantic web tools (Protégé).

## Where a New Term Goes

Five rules, applied in order, decide which file a newly needed class or property belongs in. They
exist because three partial rules were already stated in different places and collided the first
time a real organization's form was modeled.

1. **Subject is a record, document, or possession** → that thing's own `other/*.ttl`. A property
   describing an `idoc:Passport`, a `pets:Pet`, or an `education:EducationRecord` goes with that
   class. `persona.ttl` keeps only the thin `hasX` link into it.
2. **Subject is the person, and an external standard the project already aligns to defines the
   field** (CCO, JSContact/RFC 9553) → `persona.ttl`. This is why the whole JSContact layer lives
   there, and why adding `'mobile'` to `p:phoneFeature`'s vocabulary was a fix rather than a
   judgment call: RFC 9553 defines it and the list had omitted it.
3. **Subject is the person, no standard defines it, but a recognizable class of asker would want
   it** → a shared peer ontology in `persona-ext/`. `other/` never takes a property whose domain is
   `p:Person`. The subject counts as the person whether the property hangs off them directly or off
   a BFO role or quality inhering in them (`dp:jobFunction` sits on CCO's Occupation Role); what
   sends a term to `other/` is an *independent* continuant subject, not merely an indirect one.
4. **Only one organization would ever ask, in its own words** → that organization's own ontology,
   published as a `pod-category-ext/` bundle.
5. **Overriding 1–4**: if what is organization-specific is *which values are allowed, how many, and
   whether the field is required*, that is a **shape**, not vocabulary. It belongs in that
   organization's `*-shacl.ttl` and mints no new namespace.

Rule 5 does most of the work, and is easy to skip past. Precedent: `vehicles:fuelType` is declared
bare in `other/vehicles.ttl` with its frozen value list in `other/shacl/vehicles-shacl.ttl`.
Modeling the Boston Hub Society's two-page directory form produced ~32 fields, and rule 5 left
rule 4 with nothing at all: every term went to `persona.ttl`, `other/education.ttl`, or
`persona-ext/directory-profile.ttl`, and what BHS publishes is one SHACL shape —
`bhsshapes:MemberShape` — saying which of those shared fields it requires, caps, and enumerates.
Another society's form would be another shape over the same vocabulary. Reach for rule 4 only when
a term's *meaning*, not merely its permitted values, is particular to one publisher.

## Core Files

Every core file — the ontologies, their SHACL shapes, the helper scripts, the vendored subsets in `project_files/`, `app-behavior.md`, and `pod-databook.md` — is listed with its purpose in [core-files.md](core-files.md).

**SHACL directory convention**: Every `*-shacl.ttl` shapes file lives in a `shacl/` subfolder placed directly below the ontology file(s) it validates. The foundational ontologies' shapes live in the repo-root `shacl/` (e.g. `shacl/persona-shacl.ttl`, `shacl/pod-shacl.ttl`); each `other/*.ttl` peer ontology's own shapes live in `other/shacl/` instead (`other/shacl/pets-shacl.ttl` for `other/pets.ttl`, `other/shacl/vehicles-shacl.ttl` for `other/vehicles.ttl`, `other/shacl/identity-documents-shacl.ttl` for `other/identity-documents.ttl`). The same holds one level out: `persona-ext/shacl/` for `persona-ext/*.ttl`, and `pod-category-ext/shacl/` for `pod-category-ext/*.ttl`. Apply this pattern to any future peer ontology or extension. The whole set is therefore reachable by the recursive `**/shacl/*.ttl` glob, which is what integrity.md's TTL-2/TTL-3/TTL-4 rely on.

## Architecture

### Three-Layer Design

```
Triplestore (Fuseki) — loads all DataBook files directly:
  ├─ persona.ttl              (application profile — imports domain ontologies)
  │   ├─ PersonOntology.ttl
  │   ├─ AddressOntology.ttl
  │   └─ StagingOntology.ttl → BFO terms
  ├─ example/Pods/Work/Acme/Employees/Paula Walker/Paula Walker(employees).databook.md      (embeds graphs 06, 20)
  ├─ example/Pods/People/Immediate Family/Sophia Walker/Sophia Walker(immediate-family).databook.md  (embeds graphs 05, 07, 21)
  ├─ … (all other pod-databooks, each embedding one or more numbered graphs via tpod.member/tpod.tool)
  └─ example/Pods/People/Immediate Family/Sophia Walker/Health & Wellness/Health & Wellness.databook.md  (embeds graph 17)

shacl/persona-shacl.ttl — no owl:imports of data; validated against the loaded dataset
shacl/contactinfo-shacl.ttl — per-template shapes for ContactInfo files (only template with no category concept of its own)
other/shacl/medical-appointments-shacl.ttl — per-template shapes for medical appointment files
other/shacl/service-accounts-shacl.ttl — per-template shapes for service account files
other/shacl/banking-shacl.ttl — per-template shapes for debit card and checking account files
other/shacl/residences-shacl.ttl — per-template shapes for residence files
other/shacl/itineraries-shacl.ttl — per-template shapes for trip itinerary files
other/shacl/identity-documents-shacl.ttl — per-template shapes for birth certificate, driver's license, and passport files
```

1. **Foundation**: BFO (Basic Formal Ontology) — provides temporal modeling (`TemporalInterval`) and core relations
2. **Domain Ontologies** (in `project_files/`): PersonOntology, AddressOntology, StagingOntology
3. **Application Ontologies** (peer, not nested):
   - `persona.ttl`: aggregates domain ontologies; uses annotation properties (`usesRequiredClass`, `usesOptionalClass`, `usesCCOClass`, `usesCCOProperty`) to document Tellipod's usage
   - `pod.ttl`: defines `pod:Pod`, the content facet of a pod (graph links common to all pods), split into two disjoint kinds — `pod:TemplatePod` (a reusable class-level template) and `pod:InstancePod` (an actual pod instantiated in a user's own tree, carrying member composition and zero or more `pod:tool` values); also defines the graph-DataBook hierarchy `pod:Graph` → `pod:CGraph` → its disjoint leaves `pod:MemberGraph`/`pod:FormGraph`, and their `shape`/`claimant`/`subject` vocabularies, plus the `pod:Tool` hierarchy and its `formTopic`/`formGraph`/`formShape` vocabulary, since a graph DataBook only ever exists to be linked from a pod
   - `pod-categories.ttl`: defines a `skos:ConceptScheme` (`podcat:PodCategoryScheme`) of plain `skos:Concept` individuals — no `podcat:Category` class, no tree-position facet at all; a pod's parent is per-member state in that member's own store with no RDF individual at all, and `pod:category` (pod.ttl) is the sole remaining RDF-level record of a pod's matched classification; no separate canonical folder class either — the canonical tree is the concept scheme itself; carries no `owl:imports` at all

### Pod DataBook File Format

The `.databook.md` file format — development scaffolding that will not exist once the app ships, since a pod's structured content lives inside the app; the filename convention (`<local>(<catType>).databook.md`, the `custom` literal, the compression rule), the six document frontmatter fields, the `tpod:` block and its `member`/`tool` entries, the flat `graph-<NN>` id pattern with its `claimant`/`subject`/`formTopic` vocabularies, and the `### Graph NN` body structure — is specified in [pod-databook.md](pod-databook.md). None of it is documented here; edit that file instead.

### Key Architectural Patterns

**All data belongs to graphs**: every substantive fact lives in the graph it belongs to, and every graph is self-contained — it re-asserts the bare `rdf:type` of each named individual it references rather than borrowing it, so one extracted graph is complete RDF on its own. There is no separate file holding a user's identity data. See [Self-Containment](pod-databook.md#self-containment) in pod-databook.md.

**`:Self` IRI convention**: the user's own `persona:Person` individual is always `:Self`; everyone else gets a locally-minted named IRI. `:Self` is local and never exposed over the PDN, so instances never collide on it — in the example tree it is Alice throughout, whoever authored the claim. See [`:Self` and Locally-Minted IRIs](pod-databook.md#self-and-locally-minted-iris) in pod-databook.md.

**Pod/Category split**: a **pod** is the atomic unit of a user's own instance tree — a unit the app manages and holds entirely in its own protected store, pods nesting inside pods to form the tree. Tellipod persists no data in the user's filesystem at all, so there is no folder standing for a pod and nothing recording a pod's position: a pod's parent is per-member state in that member's own store, never shared content. See [storage.md](storage.md) for that decision, and [pod-databook.md](pod-databook.md) for the on-disk tree this repo carries instead, which is development scaffolding in its entirety — the `.databook.md` files and the folder layout around them alike. The RDF-level trace of a pod's classification is `pod:category`, pointing at a genuine `skos:Concept` individual (e.g. `podcat:Passport`) recording the concept the pod was originally instantiated as, fixed at creation and never re-derived from the pod's current name or position. The *canonical* side of the split — which categories have reusable starter content — lives entirely in `pod-category-templates.ttl`, each of whose `pod:TemplatePod` individuals names its own concept via `pod:category` (`pod-categories.ttl` carries no reverse pointer of its own); there is no separate canonical-instance tree. A pod's own **name** is shared content rather than a per-peer choice — see app-behavior.md's [Naming, Renaming, and Sharing](app-behavior.md#naming-renaming-and-sharing).

**Terminology going forward**: the `podcat:PodCategoryScheme` SKOS concept scheme (`pod-categories.ttl`) is a completely separate tree from a user's own instance tree — it's a recommended pattern (`pod:category`) that a pod's tree position may optionally follow, not the tree itself. Describe the user's own instance tree only in terms of **pods** and their **descendant pods** — never "folders" or "categories" — except where the subject really is this repo's scaffolding tree on disk — `app-behavior.md`'s own Scaffolding section, `storage.md`'s scaffolding-boundary section, `integrity.md`'s scaffolding checks, and throughout `pod-databook.md` — where "folder" is the correct literal term for what those describe. Never use it for a pod as the app holds one. **Two senses of "scaffold", never to be conflated**: a **scaffold pod** is a structural placeholder pod in a user's tree — a branch node such as *Companies* or *Work* whose real content lives in its own leaf pods. **Development scaffolding** is something else entirely: this repo's on-disk representation of the example tree (the `.databook.md` files and the folder layout around them), which no running Tellipod produces — see [storage.md](storage.md). The forms are kept apart mechanically: the bare noun **scaffold** modifies a pod ("scaffold pod", "scaffold box"), and the **-ing** form is reserved for the repo-artifact sense ("development scaffolding", "a scaffolding check", "scaffolding only"). Never write "scaffolding pod", "scaffolding box" or "scaffolding folder" for a pod, and never run a find-and-replace across the word without checking which sense each hit carries.

A heading, check, or script comment that names a filename/tree-position convention after "Category" (e.g. the retired "Category/Pod DataBook Filename Convention" name) is stale leftover from when a separate `category-databook` file type existed (see the Pod/Category split note above) — fix it to name the pod-level concept it actually describes.

**DataBook IRI convention**: see [Graph Ids and Named Graphs](pod-databook.md#graph-ids-and-named-graphs) in pod-databook.md.

**Peer name pattern** (not hierarchical): All name types (FullName, GivenName, FamilyName, AlternateName) connect directly to a `persona:Person` via `ont00001879` (designated by). They are siblings, not nested under a PersonName parent.

**Address history pattern**: `AddressDesignation` links Person → Address → `TemporalInterval`. Open-ended intervals (no `hasEndDate`) indicate current address.

**Named graph scoping of `BFO_0000115`**: When a Social Network individual carries `BFO_0000115 :Sophia_Walker`, the triple is intentionally scoped to the enclosing named graph — it refers to Sophia Walker *as a person entity*, with graph-specific isolation provided by the DataBook named graph architecture, not by the triple itself. Queries needing graph-specific member data must target the relevant named graphs (e.g. graph 21 + graph 7) rather than querying the full merged dataset. Do NOT change the range of `BFO_0000115` to a document IRI (breaks BFO semantics — range must be a continuant, not a document), and do NOT introduce graph-specific person individuals (reintroduces the complexity that removing the layered Persona model eliminated). RDF-star annotation is a valid future option if tooling matures.

### Key Identifiers

Classes and properties use numeric IRIs. The most common:

- `ont00001262` = Person
- `ont00001879` = designated by (Person ← name/identifier)
- `ont00001765` = has text value (designator → literal string)
- `ent00000001`–`ent00000006` = name types (FullName, GivenName, AdditionalName, FamilyName, Suffix, AlternateName)
- `ent00000008` = SSN; `ent00000023` = Phone; `ent00000024` = Email
- `ent00000010` = PostalAddress; `ent00000016` = AddressDesignation
- `BFO_0000038` = TemporalInterval; `ent00000017/18` = hasStartDate/hasEndDate

## Versioning

Before committing any change to `persona.ttl`, increment the **minor version number** in that file's `owl:versionInfo` annotation and update the description to summarize the change. For example:

```
owl:versionInfo "Version 3.0.3 - added social network"@en
```
becomes:
```
owl:versionInfo "Version 3.0.4 - added birth date"@en
```

`pod.ttl` and `pod-categories.ttl` do not carry `owl:versionInfo` at all — these two files are evolving too rapidly right now for a change-log annotation to be worth maintaining. Do not add it to either. They still carry `owl:versionIRI` and `dc:date`; bump those on a real change if convenient, but there's no change-history text to update alongside them. `organization.ttl`, `pod-category-templates.ttl`, `service.ttl`, each `other/*.ttl` peer ontology, each `persona-ext/*.ttl` extension ontology, and each `pod-category-ext/*.ttl` bundle are unaffected by this — they still carry `owl:versionInfo` and should keep it updated on a real change, the same way `persona.ttl` does. The `project_files/*.ttl` vendor subsets (`dron-upper.ttl`, `ncbitaxon-subset.ttl`, `vbo-subset.ttl`, `prov-upper.ttl`, `wikidata-vehicle-makes-subset.ttl`, `wikidata-vehicle-models-subset.ttl`) also carry `owl:versionInfo`, bumped the same way, even though they aren't listed among the "foundational" files above — a vendor file's own hand-curated subset can grow over time just like any other file here.

**`owl:versionInfo` describes only the current version — no embedded history, ever**: `persona.ttl`, `organization.ttl`, `pod-category-templates.ttl`, `service.ttl`, each `other/*.ttl` file, and each `project_files/*-subset.ttl`/`project_files/dron-upper.ttl`/`project_files/prov-upper.ttl` vendor file each keep `owl:versionInfo` as a single bare `"Version X.Y.Z - <description of this change only>"@en` string. **Never embed history in it** — replace the whole string with the new version and its own description on each bump; never append the outgoing description in parentheses. Git carries the changelog now — the same reasoning that governs `rdfs:comment`/block-comment text in every `.ttl` file (describe current semantics only, never narrate how it got that way) applies to `owl:versionInfo` too.

**No `owl:versionInfo` in any `*-shacl.ttl` file, ever**: `shacl/pod-shacl.ttl`, `shacl/persona-shacl.ttl`, `shacl/organization-shacl.ttl`, `shacl/contactinfo-shacl.ttl`, `shacl/service-shacl.ttl`, and every `other/shacl/`, `persona-ext/shacl/`, and `pod-category-ext/shacl/` shapes file carry no `owl:versionInfo` — this applies uniformly to every SHACL shapes file regardless of whether its paired main ontology file still carries `owl:versionInfo` (`shacl/persona-shacl.ttl` does not, even though `persona.ttl` itself does). Every one of these files still carries `owl:versionIRI` and `dc:date`; bump those on a real change, but do not add `owl:versionInfo` to any of them — their `rdfs:comment`s describe only current semantics, same as the main ontology files.

## Integrity Checks

All integrity checks live in [integrity.md](integrity.md), along with the scripts that run them. Run the relevant ones after any change to a graph (its `tpod.member`/`tpod.tool[].graph` entry or `### Graph NN` body section) or a pod DataBook. Files inside any directory named `under-development/` (at any depth) are works-in-progress and are excluded from all of them.

Checks are grouped by **what the check reads**, and numbered from 1 within each group, the prefix being part of the identifier: **`PNG-n`** (a diagram image), **`TTL-n`** (a `.ttl` file, asking about triples — these and only these parse with `rdflib`), **`YAML-n`** (a pod DataBook's frontmatter and body as written), and **`FS-n`** (the filesystem and the docs referring to it). Run and report them kind by kind, announcing the kind and then working through its checks in order. Never cite a bare `Check <number>`: the old flat numbering is retired, and integrity.md's Renumbering section carries the old → new map.

## Keeping Files in Sync

Whenever changes are made to any graph file, `persona.ttl`, or `pod.ttl`, `shacl/persona-shacl.ttl` must be updated to match:

- **New property usage in a graph** (e.g., a new physical characteristic, relationship, or identifier added to a Person or Persona instance) → add or extend a SHACL shape to validate that property on the relevant target class.
- **New class or property defined in `persona.ttl`** (e.g., `persona:hasSocialNetwork`) → add a SHACL shape that constrains how instances of the domain class may or must use it.

Always update `shacl/persona-shacl.ttl` in the same edit session as the change that triggers it.

## Validation

**SHACL validation** (e.g., using Apache Jena's `shaclvalidate`) — run against turtle extracted from a single embedded graph (see example.md's Validation section for the full extraction pipeline; graph 14 is embedded in this pod):
```bash
python3 helpers/extract-graph.py "example/Pods/Groups/Boston Hub Society/Boston Hub Society.databook.md" graph-14 > /tmp/data.ttl
shaclvalidate -datafile /tmp/data.ttl -shapesfile shacl/persona-shacl.ttl
```

**Protégé**: Load `persona.ttl`; Protégé will import the domain ontologies via IRI resolution. Use the reasoner (HermiT/Pellet) to check consistency.

## Diagrams and the Pre-Commit Hook

`hooks/pre-commit` (installed with `cp hooks/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit`) regenerates the `.mmd` and `.png` for every graph in a staged pod DataBook and stages the results alongside it, so a diagram never drifts from the graph it draws.

**`helpers/draw.py` is not byte-deterministic**: it rehashes its literal node ids on every run, so a regenerated `.mmd` diffs even when the diagram is structurally identical (`n655e442e50be -->|"GivenName"| ndc1b5183f88e` becomes the same edge with a different hash). Staging a DataBook therefore redraws its diagrams whether or not their content changed.

**Use `SKIP_DRAW=1 git commit` for a commit that edits DataBook prose without changing any graph's triples** — a reworded Overview, a corrected cross-reference, a typo fix. Without it, such a commit carries dozens of regenerated images whose only difference is the rehash, burying the real change and making the commit message's account of what moved inaccurate. Redraw deliberately instead, by running `helpers/draw.py` on the graphs whose Turtle actually changed (see [example.md](example.md#diagrams)).

Two things to know about installing it. `.git/hooks/` holds a *copy*, not a link, so **reinstall after any change to `hooks/pre-commit`** or commits keep running the old one. And `mmdc` must be on `PATH` for the `.png` half; without it the `.mmd` is still rewritten, with a warning and no image.

## README Coverage

**README is theory; example.md is the worked example.** `README.md` describes what a term or mechanism *is* and why it exists, in the general case. The Alice Walker scenario — her pods, her graphs, the specific people, organizations and documents in it — lives in `example.md`, and `README.md` links to it rather than retelling it. Concretely, when documenting something new in `README.md`:

- Name the classes, properties, files and rules. Explain the design and the reasoning.
- Do **not** name a specific example individual, pod, organization, or graph number (`:Alice_Walker`, the Citibank pod, `graph-14`, the Boston Hub Society) to carry the explanation. If the mechanism can only be explained by walking through one, the walk-through belongs in `example.md` behind a link.
- A one-line pointer at the end of a section — "for a worked X, see `[example.md](example.md#anchor)`" — is the right amount, and is all of it that belongs in `README.md`.
- The same holds for a newly published extension or peer ontology: `README.md` gets the mechanism and the term list, `example.md` gets the instance that exercises it.

Pre-existing prose that describes a README-embedded *diagram* (e.g. the Representative Pods section, which names the boxes drawn in `images/representative-pods.png`) is the one standing exception — the diagram is in `README.md`, so its caption has to be too.

Documentation is split across five files: `README.md` documents the ontologies themselves (Category, Pod, Graph, Persona, Pets, Organization); `example.md` holds the worked Alice Walker example, diagram-generation instructions, and the full validation pipeline (linked from the bottom of `README.md`); `storage.md` is the canonical statement that Tellipod persists no data in the user's filesystem — all pod content lives in a protected, app-managed store, encrypted at rest — and draws the boundary between what ships as Tellipod (the `*.ttl` ontologies and their shapes) and what is development scaffolding (the `.databook.md` files, `example/Pods/`, the folder layout, `helpers/`, and the filesystem-bound integrity checks); `app-behavior.md` documents app-level behavior built on top of the ontologies — pod lifecycle, storage, sharing/permissions, naming/renaming, pod contents, and the auto-filing heuristic (linked from both `README.md` and `example.md`); `pod-databook.md` specifies the `.databook.md` file format itself — filename convention, frontmatter fields, the `tpod:` block, and the `### Graph NN` body structure (linked from `README.md` and `CLAUDE.md`). ## Catalog Files

Two `catalog-v001.xml` files map ontology IRIs to local file paths so Protégé can resolve `owl:imports` without hitting the network:

- **`catalog-v001.xml`** (repo root) — used when opening root-level files (`persona.ttl`, `shacl/persona-shacl.ttl`, etc.) directly. Uses **relative** paths from the repo root.
- **`example/catalog-v001.xml`** — used when opening a graph file from the `example/` directory directly. Uses **absolute** `file://` paths.

**Whenever a `.ttl` file is created, deleted, renamed, or moved**, update both catalog files to match:
- **Create**: add a `<uri>` entry in both catalogs with the new file's ontology IRI (from its `rdf:type owl:Ontology` declaration) and its path.
- **Delete**: remove the corresponding `<uri>` entry from both catalogs.
- **Rename or move**: update the `uri=` path attribute in both catalogs.

The `id` attribute is a human-readable label (no functional significance); keep it consistent with the file's short name or diagram number.

## Gitignore Notes

`.gitignore` covers `.claude/*` (with `!.claude/commands/` re-including the project's own slash
commands), `.DS_Store`, `__pycache__/`, `*.pyc`, and `YAML-SYNTAX.md`.
