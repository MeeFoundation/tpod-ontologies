# Core Files

The project's core files and what each one is for — split out of [CLAUDE.md](CLAUDE.md) to keep that file smaller. The integrity checks these files are subject to live in [integrity.md](integrity.md).

| File | Purpose |
|------|---------|
| `persona.ttl` | Persona ontology — imports domain ontologies, annotates which classes/properties are required vs. optional for V4, defines `p:Person`, the thin `hasX` link properties into the `other/` peer ontologies (`persona:hasPet`, `persona:hasVehicle`, `persona:hasIdentityDocument`, `persona:hasBankAccount` — each referenced by name with no `owl:imports` in either direction), the physical-card/wallet classes, `persona:hasSocialNetwork`, and the whole JSContact (RFC 9553) alignment layer: `p:ContactInfo` (the one template type label class this file declares — a label only, never asserted via `rdf:type`), the designator classes `persona:Credential`/`persona:WebURL`/`persona:OrganizationUnit`/`persona:JobTitle`, the annotation properties `persona:contactContext`/`persona:phoneFeature`/`persona:serviceLabel`, `persona:hasPhoto`, and `persona:Anniversary`/`persona:PersonalInfo`/`persona:PersonalityAssessment` with their own properties. Also defines `persona:specialty` (a physician's medical specialty, domain `persona:Person` directly — it describes the physician, not any appointment record — backing the tool `cat:PrimaryCarePhysician` declares). The rule that decides what belongs here: a property whose domain is `persona:Person` directly, an annotation property, or a thin `hasX` link into a domain modeled elsewhere; every record/document class a person merely *has*, and every property whose domain and range both sit outside `persona:Person`, lives in its own `other/*.ttl` peer ontology instead |
| `pod.ttl` | Pod ontology — `pod:Pod`, the content facet of a pod, carrying only what's common regardless of facet: `category` — range `skos:Concept`, at most one value (0..1; absent/nil exactly when the pod is of the UserDefined category, identified precisely by the pod carrying no category value at all, mirrored in this repo's scaffolding by its pod-databook filename's `(custom)` disambiguator), else the category concept (a genuine `skos:Concept` individual scoped to `cat:CategoryScheme` — no class-value punning, since category.ttl's tree is SKOS, not OWL classes) it was originally instantiated as, fixed at creation rather than re-derived from the pod's current name, letting a recipient's app use it as a filing hint, referenced by name without `owl:imports category.ttl` (mirroring `creator`'s identical pattern below); does not contradict `pod:Pod`'s "no link to a tree position" design (see integrity.md's PNG-3), since `skos:Concept` is the classificatory hierarchy — a pod's parent is per-member state in that member's own store, never shared content and never modelled here (see storage.md). Splits into two disjoint kinds (`owl:disjointWith` — a pod is always exactly one, never both): `pod:TemplatePod` (abstract, a reusable class-level template — carries `category` (the category concept it's a template for), `memberShape` (0..N) and `declaresTool` (0..N `pod:Tool` nodes, each carrying its own `formShape`)) and `pod:InstancePod` (concrete, an actual pod instantiated in a user's own tree — carries `creator`, `owner`, `member`, and 0..N `tool` values). There is no `shape` property any more — a `InstancePod`'s applicable validation shape is derived, not stored: reverse-lookup the `TemplatePod` sharing the same `category` value and read either its `memberShape` or the `formShape` of the matching declared tool, whichever applies to the graph in question (`member` vs. a tool's own graph), directly (the same reasoning by which a pod stores no subject of its own — `pod:subject` is scoped to `pod:MemberGraph`, naming the party whose member entry a graph is, never what the pod is about). There is no further pod subclass: what varies from pod to pod is which tools it carries, which `tool` records as a count from zero upwards rather than as a type. `InstancePod` additionally carries the two tag properties `userTag` (`owl:DatatypeProperty`, range `xsd:string`) and `serviceTag` (`owl:ObjectProperty`, range `ServiceTag`), each 0..N, no fixed upper bound — retrieval labels orthogonal to `category`'s single filing hint: a pod sits in at most one category but may carry any number of tags. A tag's *kind* is carried entirely by which of the two properties holds it; there is no kind marker. The two differ in shape because they differ in author: a `userTag` is a bare string a person types, needing no qualification since one user's own tree has no second author to collide with, while an `serviceTag`'s value is an `ServiceTag` node (also defined here, outside the `Pod` hierarchy) carrying `tagNamespace` (the writing module's developer's own DNS domain, reverse-DNS), `tagKey` (which kind of external fact it records) and `tagValue` (the label), each `xsd:string` and required exactly once. Their domain is `InstancePod`, not `Pod`, deliberately — a `TemplatePod` seeds no tags, so none is ever cloned by Lazy Instantiation (the opposite placement from `category`). There is no third, app-supplied kind and no built-in tag vocabulary: a set of pods sharing a fact the data already models is found by searching for that property instead (e.g. `serviceaccounts:loyaltyProgramID`). `userTag` (free text) is ordinary shared pod content, propagating to every member on a share; `serviceTag` — written by one member's own service module for its own bookkeeping, never displayed but still searchable — is the sole piece of a pod's content that is **never** propagated, since each principal runs their own agent independently and the value would be uninterpretable in an instance running a different service or none. See integrity.md's YAML-9. `creator`'s range is `p:Person`, referenced by name without importing that ontology (the same by-name pattern `claimant`, below, uses for its own wider three-way union), required exactly one value, since every actual pod's content is authored by someone. `owner` (same range as `creator` — never a `service:Service`) identifies which of the pod's members hold the owner role rather than the regular (non-owner) member role every other member defaults to — required, one or more values, no fixed upper bound; `creator`'s own value is always included as the pod's initial owner, and any current owner may promote any other current regular member (never a service) to owner, or demote another owner back to regular-member status (the `sh:minCount 1` floor keeps a pod's last remaining owner from being demoted) — see integrity.md's YAML-7. `member` is an `owl:ObjectProperty` (range `pod:MemberGraph`, domain `InstancePod`) — the required per-member baseline, one or more values enforced by `shacl/pod-shacl.ttl`'s `:InstancePodShape`, no fixed upper bound; `tool` (range `pod:Tool`, domain `InstancePod`, 0..N) links to the objects the pod carries beyond that baseline — a form, a calendar, a drawing canvas or a map, each with its own data format and its own UI contribution, of which only the format is modelled here. `pod:Tool` (abstract) carries no property of its own and splits into `pod:Form`/`pod:Calendar`/`pod:Canvas`/`pod:Map`; only `Form` has a content model, and all three tool-content properties are scoped to it — `formTopic` (`xsd:anyURI`, exactly one value on a live form tool), `formGraph` (range `pod:FormGraph`, at least one value, capped in practice at the pod's own member count per tool — see integrity.md's YAML-8) and `formShape` (range `sh:NodeShape`, 0..N, carried only in the declared-tool role). Nothing is hoisted onto the abstract class, since the three stub kinds have no data format of their own to make anything common. `memberShape` (domain `pod:TemplatePod`) and `formShape` (domain `pod:Tool`, carried only in the declared-tool role), range `sh:NodeShape`, each 0..N, link a template pod to its SHACL shape(s) describing what a `member`/`topic` graph (respectively) filed under its category should look like. Every individual in `cat-templates.ttl` is typed solely `pod:TemplatePod` — never also `pod:InstancePod`, since the two kinds are disjoint. Carries no record of a pod's tree position at all — that is per-member app state with no RDF individual; `category` is the sole remaining record of a pod's original classification. Also defines the graph-DataBook hierarchy — `pod:Graph` (abstract) → `pod:CGraph` (abstract) → its two `owl:disjointWith` leaves `pod:MemberGraph` (`member`'s range) and `pod:FormGraph` (`formGraph`'s range), neither with subclasses of its own — and their `shape`/`claimant`/`subject` annotation properties: controlled vocabularies for classifying graph files. `shape` (domain `Graph`, 0..N) names the shape a graph should validate against; `claimant` (domain `CGraph`, range a union of `p:Person`/`o:Organization`/`service:Service`) is who claimed the data; `subject` (domain `MemberGraph`, `xsd:anyURI`) is the party whose `member` entry the graph is; a `FormGraph` carries no about-ness property of its own, its topic being the holding tool's single `formTopic` (`xsd:anyURI`) — any resource IRI, and deliberately not required to be a person's identity or to map to a PDN node subject identity at all, which is precisely what the two leaves exist to distinguish, since `claimant` and `subject` always do. The four self-vs-other combinations a member graph distinguishes (self-by-self, other-by-self, other-by-other, self-by-other) are derived directly from `subject`/`claimant`. A graph DataBook only ever exists to be linked from a pod (via `member`/`topic`), so its classification vocabulary lives in this same file rather than a separate one |
| `category.ttl` | Category taxonomy — a `skos:ConceptScheme` (`cat:CategoryScheme`), not an OWL class hierarchy: every category is a plain `skos:Concept` individual (there is no `cat:Category` class), rooted at two top concepts (`cat:Person`/`cat:Organization`, `skos:hasTopConcept`) and connected to every narrower concept via `skos:broader` (asserted child → parent, one self-contained block per concept, scoped via `skos:inScheme cat:CategoryScheme`) — a deliberate fix over an earlier `rdfs:subClassOf` design that wrongly implied OWL subsumption (`cat:Pets rdfs:subClassOf cat:Person` reads as "every Pet is a Person"; `skos:broader` carries no such entailment). No tree-position facet at all: a user's own instance-tree position is per-member app state, with `pod:category` (pod.ttl) the sole remaining RDF-level record of a pod's matched classification. No `cat:templatePod` property (removed) — a templated category's reusable content is found via `cat-templates.ttl`'s own `pod:TemplatePod` individuals, each carrying its own `pod:category` value naming the concept it's a template for, a reverse lookup rather than a forward pointer. Carries no `owl:imports` at all any more, since nothing in it references a `pod:` term |
| `cat-templates.ttl` | Class-level `pod:Pod` templates, 106 in total — one individual per category concept in `category.ttl`, the two SKOS top concepts `cat:Person`/`cat:Organization` included (see integrity.md's TTL-6 — a pod may legitimately be instantiated as either), each carrying its own `pod:category` value naming that concept — the reverse of the deleted `category.ttl`'s `cat:templatePod` forward-pointer — plus one more, `ctpl:UserDefinedTemplatePod`, with **no** `pod:category` value at all: the fallback template for a pod created with no category selected (the Custom/UserDefined case), found as the unique category-less `pod:TemplatePod` rather than by the usual reverse lookup. Each is typed solely `pod:Pod, pod:TemplatePod` — `pod:TemplatePod` and `pod:InstancePod` are disjoint, so a template pod carries no member composition of its own, just its shape property/properties pointing to SHACL shape(s) — in `shacl/persona-shacl.ttl`/`shacl/contactinfo-shacl.ttl` for a template targeting a `persona:`-defined class, otherwise in the `other/shacl/<name>-shacl.ttl` file paired with whichever `other/*.ttl` peer ontology declares that template label class (`petshapes:`, `vehicleshapes:`, `idocshapes:`, `mashapes:`, `sashapes:`, `bankingshapes:`, `residenceshapes:`, `itineraryshapes:`) — following two patterns: (1) `pod:memberShape pshapes:ContactInfoShape` plus a `pod:declaresTool` node whose `pod:formShape` carries the category's own record shape — the 18 whose real content is held by a form tool instead (Passport, SSN, BirthCertificate, DriversLicense, MedicalAppointment, PetMedications, PetProfile, VehicleProfile, Companies, BankingPayments, Home, Trips, TravelProvider, Groups, Organization — each a real reified document/account/organization type, TravelProvider's being the loyalty/service account held with that provider — plus HealthWellness, PrimaryCarePhysician, and PetsCareAndFeeding, each a more modest shape with every property optional) — `cat:BankingPayments`'s declared tool carries three `pod:formShape` values at once (`ServiceAccountShape`, `DebitCardShape`, `CheckingAccountShape`), since a single Citibank-claimed tool graph there holds all three templates' content together — `cat:PrimaryCarePhysician` similarly carries two (`PrimaryCarePhysicianShape`, `ContactInfoShape`), since Dr. Jane Starostina's own tool graph (graph-25) doubles as both her optional specialty record and a contact-info profile; (2) `pod:memberShape pshapes:ContactInfoShape` alone, declaring no tool — every other templated category (88 of them, including `cat:People` and three of its four direct `skos:broader` children, and every other category with no document type or tool content of its own), plus `ctpl:UserDefinedTemplatePod`. **`pod:memberShape pshapes:ContactInfoShape` is asserted directly and identically on every one of the 106 individuals in this file, with no exception** (integrity.md's TTL-7). That uniformity is scoped to this file on purpose: a `pod:TemplatePod` published by a category extension (`category-ext/`) may name any member shape it likes, and `bhscat:BostonHubSocietyTemplatePod` is the first to do so — not hoisted onto the `pod:TemplatePod` class itself via an OWL restriction, since nothing in this project's validation pipeline runs a reasoner to materialize such an entailment. Whether a template declares a tool, or not, is the whole of what it says on the matter — there is no separate boolean, since declaring the tool already says it, and a second statement could only ever disagree with the first. What a template declares constrains only what Lazy Instantiation produces, never what the resulting pod may later hold: any pod may gain further tools at any time, chosen by the user. Imports `pod.ttl` directly — no mutual import with `category.ttl` |
| `shacl/pod-shacl.ttl` | SHACL validation shapes for `pod:Pod` DataBook instances, split across shapes matching `pod.ttl`'s two-kind split: `:PodShape` (target `pod:Pod`) — `category` cardinality (at most one — 0..1 — constrained via `sh:class skos:Concept` plus a nested `skos:inScheme cat:CategoryScheme` check, now that category.ttl's tree is genuine SKOS individuals rather than class-value-punned classes), plus an `sh:xone` requiring `rdf:type` to be exactly one of `pod:TemplatePod`/`pod:InstancePod` (mirroring `pod.ttl`'s `owl:disjointWith`); `:TemplatePodShape` (target `pod:TemplatePod`) — `memberShape`/`formShape` cardinality (zero or more values each, no fixed upper bound; deliberately not constrained to `sh:class sh:NodeShape` since their values are only typed as such in the per-template `*-shacl.ttl` files, which the pod pass excludes from its shapes) and `declaresTool` cardinality (0..N, each a `pod:Tool`); `:InstancePodShape` (target `pod:InstancePod`) — `creator` (required, exactly one value) constrained to be a `p:Person`, `owner` (required, one or more values, no fixed upper bound, each constrained to be a `p:Person`, never a `service:Service`), `member` (required, one or more values, no fixed upper bound, each constrained to `pod:MemberGraph`), and `userTag`/`serviceTag` (each zero or more values, no `sh:minCount` and no `sh:maxCount`; neither gets an `sh:in` list, since a tag belongs to no vocabulary at all, unlike `vehicles:fuelType`'s and `pets:sex`'s genuinely frozen ones). `userTag` is held to a non-empty `xsd:string` (`sh:minLength 1`), leaving whitespace, YAML type confusion and duplication to integrity.md's YAML-9, none being SHACL-observable for a bare literal; `serviceTag` is held here only to its value's kind (`sh:class ServiceTag`, `sh:nodeKind sh:BlankNodeOrIRI`), with the node's own three parts constrained by `:ServiceTagShape` — each required exactly once and pattern-checked (reverse-DNS namespace, identifier-token key, non-empty single-line unpadded value), which leaves YAML-9 only what SHACL still cannot reach there: a non-string YAML sub-value, an entry that isn't a mapping, an extra sub-key, and a repeated `(namespace, key, value)` triple. There is no `shape` shape any more — a `InstancePod`'s validation shape is derived via its own `category` value, never stored, so there's nothing to constrain; there is likewise no SHACL constraint tying `owner` to `creator`/`member` — that invariant is checked only by integrity.md's YAML-7; `:LiveToolShape` (objects of `pod:tool` — targeting `sh:targetObjectsOf` rather than a class, since the same tool classes also serve the declared role) — `formTopic` required exactly once, each `formGraph` value a `pod:FormGraph`, and no `formShape`; `:DeclaredToolShape` (objects of `pod:declaresTool`) mirrors it — `formShape` only, and neither `formTopic` nor `formGraph`. The per-tool graph count — at least one value (SHACL sets no maximum here; the real cap — one value per pod member, each with a distinct claimant — is integrity.md's YAML-8, not a SHACL constraint), each constrained to be a `pod:FormGraph`. There is no pod-level subject property/shape at all — a pod's own subject is derived, never stored (see integrity.md's YAML-4); three graph shapes mirroring `pod.ttl`'s three levels constrain the different, graph-level properties instead. `:CGraphShape` requires `claimant` exactly once, constrained to a `p:Person`/`o:Organization`/`service:Service`; it targets `pod:MemberGraph` and `pod:FormGraph` explicitly rather than their shared `pod:CGraph` superclass, since `helpers/validate.py` runs no reasoner and the synthesized data carries only the leaf type. `:MemberGraphShape` (target `pod:MemberGraph`) requires `subject` exactly once, an IRI; `:FormGraphShape` (target `pod:FormGraph`) forbids `subject` (`sh:maxCount 0`), a tool graph's about-ness living one level up on the tool. That zero-count is how the leaves' `owl:disjointWith` becomes checkable. `formTopic` gets no `sh:class`: its value may be an individual of any `other/*.ttl` domain ontology, so nothing could enumerate what is allowed. A graph DataBook does not carry `pod:creator` (or any creator property) — that stays a `pod:Pod`-only property |
| `service.ttl` | Service ontology — `service:Service`, the member-capable class for every pod participant that is not a person, grounded as `cco:ont00001017` (CCO Agent, a BFO Material Entity bearing an Agent Capability) and `prov:Agent`. Every service the app ships is one of its classes, and every one of those classes is a service the app can run. Branches in two on whom the service acts for: `service:AgentService` (acts for exactly one `p:Person` member, named by its required `service:actsFor`; directly instantiable, and the parent of the two concrete services the app ships — `service:ChatGPT` and `service:ArcaBackup`) and `service:ServiceProvider` (an organization's own service, acting for the organization named by its `service:providedBy` — the `pod:member` subject but not the `pod:claimant` of what that organization contributes). No class is declared disjoint from any other, so one real service can be more than one kind at once. `service:providedBy` (domain `service:Service`, range `o:Organization`) is the only route by which an organization reaches a member list at all; 0..1 in general, exactly one on `service:ServiceProvider` and `service:ArcaBackup`; `service:ChatGPT` deliberately requires none, since naming the vendor is the class's own job and OpenAI is not a party to the pod's relationship. `service:AgentService` is also `prov:SoftwareAgent`, inherited by all three of its leaves. Imports CCO's `AgentOntology` and `project_files/prov-upper.ttl`; references `p:`/`o:` by name. Doc alias: `s:` |
| `shacl/service-shacl.ttl` | SHACL validation shapes for the Service ontology. `:ServiceShape` (target `service:Service`) — `providedBy` at most one `o:Organization`, `actsFor` at most one `p:Person`; `:AgentServiceShape` raises `actsFor` to exactly one, inherited by both of its leaves; `:ServiceProviderShape` and `:ArcaBackupShape` each raise `providedBy` to exactly one. `service:ChatGPT` gets no shape of its own, adding no constraint beyond the inherited one. No shape forbids `actsFor` on `service:ServiceProvider` — no class is disjoint from any other, so that would be unsatisfiable against `:AgentServiceShape`'s own minimum. Carries no `owl:versionInfo` |
| `shacl/persona-shacl.ttl` | SHACL validation shapes — constraint rules for all `persona:Person` instances (SSN format, address cardinality, payment cards, wallet, social network, etc.), plus `:SSNShape`, `:HealthWellnessShape`, and `:PrimaryCarePhysicianShape` (`cat:PrimaryCarePhysician`'s own `pod:formShape`, targeting `persona:Person` directly since a physician has no reified document individual of their own; its one optional property is `persona:specialty`). The `:DebitCardShape`/`:CheckingAccountShape` live in `other/shacl/banking-shacl.ttl` instead, paired with `other/banking.ttl` |
| `other/medical-appointments.ttl` | A small `other/` peer ontology — the claims two people share to arrange a medical appointment on someone else's behalf. Defines `medicalappointments:MedicalAppointmentRecord` (an independent template type label class, also the `rdf:type` of the reified record individual) plus its own claim properties (`forPatient`, `hasPrimaryCarePhysician`, `currentMedication`, `allergy`, `medicalHistoryNote`, `insuranceProvider`, `insurancePolicyNumber`, `insuranceGroupNumber`, `preferredPharmacy`), all domain `MedicalAppointmentRecord`. `persona.ttl` carries no thin `hasX` link into it — a record here is shared between the two coordinating members rather than possessed by one `persona:Person`. Doc alias: `ma:`. Carries no `owl:imports` |
| `other/shacl/medical-appointments-shacl.ttl` | `:MedicalAppointmentRecordShape`, linked from `cat:MedicalAppointment`'s template pod via `pod:formShape`; run against the individual graph file, not merged data |
| `other/service-accounts.ttl` | A small `other/` peer ontology — an online service account a person holds (Google, AT&T, a bank's web portal). Defines `serviceaccounts:ServiceAccount` (always multi-typed `cco:ent00000033` Online Service Account, so service name/username/service URI reuse that class's own properties directly), `serviceaccounts:hasPassword`, and `serviceaccounts:loyaltyProgramID` (a loyalty/rewards program membership number — optional, 0..1, distinct from the login user handle; present only on an account with a provider that runs such a program, `:Alice_Hilton_Account` being the one example) — both properties domain `cco:ent00000033`, internal to this domain rather than `persona:Person` properties. `persona.ttl` carries no thin `hasX` link into it: CCO's own `holds user account` (`cco:ent00000045`) already plays that role. Doc alias: `sa:`. Carries no `owl:imports` |
| `other/shacl/service-accounts-shacl.ttl` | `:ServiceAccountShape`, linked from `cat:Companies`'s, `cat:BankingPayments`'s and `cat:TravelProvider`'s template pods via `pod:formShape`; requires exactly one username and one password, and allows at most one each of service name, service URI, and `loyaltyProgramID`; run against the individual graph file, not merged data |
| `other/banking.ttl` | A small `other/` peer ontology — a debit card and the checking account it draws on. Defines `banking:DebitCard` (always multi-typed `cco:ent00000051`), `banking:CheckingAccount`, and `banking:accessesBankAccount` (domain `cco:ent00000051`, range `banking:CheckingAccount` — internal plumbing between two classes in this same file, which is why it isn't in `persona.ttl`). `persona:hasBankAccount` (domain `persona:Person`, range `banking:CheckingAccount`) stays in `persona.ttl` as the thin link. Carries no `owl:imports` |
| `other/shacl/banking-shacl.ttl` | `:DebitCardShape` (targets `cco:ent00000051` directly, since every `banking:DebitCard` individual is multi-typed alongside it) and `:CheckingAccountShape` (targets `banking:CheckingAccount`), both linked from `cat:BankingPayments`'s template pod via `pod:formShape`; run against the individual graph file, not merged data |
| `other/residences.ttl` | A small `other/` peer ontology — a place a person has lived, current or past. Defines `residences:Residence` (always multi-typed `cco:ent00000016` AddressDesignation, so its address/participant/temporal-region properties reuse that class's own pattern directly), and nothing else. `persona.ttl` carries no thin `hasX` link into it — a residence is simply the `pod:formTopic` of its own `cat:Home` pod. Carries no `owl:imports` |
| `other/shacl/residences-shacl.ttl` | `:ResidenceShape`, linked from `cat:Home`'s template pod via `pod:formShape`; run against the individual graph file, not merged data |
| `other/itineraries.ttl` | A small `other/` peer ontology — a specific trip a person is planning or taking, as distinct from `cat:Travel`'s broader loyalty-program information. Defines `itineraries:Itinerary`, alone among this project's template label classes in being multi-typed alongside nothing (no domain ontology models trip-planning data yet) and carrying no structured properties of its own beyond a human-readable `rdfs:label`/`rdfs:comment`. `persona.ttl` carries no thin `hasX` link into it. Carries no `owl:imports` |
| `other/shacl/itineraries-shacl.ttl` | `:ItineraryShape`, linked from `cat:Trips`'s template pod via `pod:formShape`; run against the individual graph file, not merged data |
| `other/pets.ttl` | The first `other/` peer ontology — pet domain-modeling kept out of `persona.ttl` (see Project Overview). Defines `pets:Pet` (template label + the pet individual's own `rdf:type`, carrying required `pets:name` (`xsd:string`) and `pets:hasSpecies` (an NCBITaxon class IRI), and optional `pets:hasBreed` (a VBO class IRI, including VBO's own "Mixed Breed" classes), `pets:birthDate` (`xsd:date` or `xsd:gYear` — exact or approximate), `pets:hasBodyWeight`/`pets:BodyWeight` (mirrors `pets:DosageAmount`'s CCO Measurement-Unit/Information-Bearing-Entity reification, but with a required rather than optional unit), `pets:sex` (`"Male"`/`"Female"`), and `pets:isSpayedOrNeutered` (`xsd:boolean`)) and `pets:PetMedicationRecord`/`pets:Medication` (`pets:hasMedication`, `pets:hasActiveIngredient` (ChEBI class IRIs), `pets:hasDoseForm` (DrOn dose-form class IRIs), `pets:DosageAmount`/`pets:hasDosageAmount` (CCO Measurement-Unit/Information-Bearing-Entity machinery), `pets:MedicationAdministration`/`pets:hasAdministration` (DrOn drug-administration process + BFO TemporalInterval), `pets:medicationFrequencyPerDay`, `pets:medicationBrandName`, `pets:medicationManufacturer`, `pets:medicationDuration`). Both are independent template type label classes, targeted directly by their own SHACL shape (`other/shacl/pets-shacl.ttl`). `owl:imports` `project_files/dron-upper.ttl`, `project_files/ncbitaxon-subset.ttl`, and `project_files/vbo-subset.ttl` |
| `other/shacl/pets-shacl.ttl` | SHACL shapes for `pets:Pet` (`:PetShape`) and `pets:PetMedicationRecord`/`pets:Medication` (`:PetMedicationRecordShape`, `:MedicationShape`, `:DosageAmountShape`, `:MedicationAdministrationShape`), each linked from its `cat-templates.ttl` template pod via `pod:formShape`; run against the individual graph file, not merged data |
| `other/education.ttl` | The ninth `other/` peer ontology — one stage of a person's schooling, kept out of `persona.ttl` the same way pet/vehicle/identity-document domain-modeling already is, and the exact parallel of `other/medical-appointments.ttl`'s `ma:MedicalAppointmentRecord`: a reified record individual, not a property of the person. Defines `education:EducationRecord` (an independent template type label class, asserted via `rdf:type` directly on the record individual and targeted directly by its own SHACL shape) carrying required `education:schoolName` plus optional `education:educationLevel` (SHACL-enumerated `"high school"`/`"college"`/`"other"`), `education:schoolCity`, `education:schoolState`, `education:yearGraduated` (`xsd:gYear`) and `education:degree` (0..N). Which stage a record represents is carried by `educationLevel` rather than by a property per stage, so a form asking for exactly one high school and one college expresses that as a cardinality constraint in its own shape rather than as vocabulary.
